# 05 评测方法及打分规则

> 模型评测方法与打分规则的详细设计，含评测框架、维度定义、题集规范、打分公式、判定基准、质量控制与脚本技术实现。

## 1. 评测框架

采用**双通道互补**评测：

| 方式 | 定位 | 优势 | 局限 |
|------|------|------|------|
| **脚本评测** | 客观量化基准 | 可复现、可批量、客观 | 难覆盖端到端场景 |
| **Agent 评测** | 真实场景验证 | 贴近实际、反映综合能力 | 标准化难度高 |

判定原则：脚本评测给出**可复现的量化分数**，Agent 评测给出**真实任务完成度**，二者加权综合判定模型能力。

## 2. 评测维度定义

| 维度 | ID | 考察能力 | 题型示例 | 规则 hints 示例 |
|------|-----|----------|----------|-----------------|
| 推理/逻辑 | `reasoning` | 数学、逻辑推理 | 鸡兔同笼、说谎者悖论 | 答案数值 `["23","12"]` |
| 代码生成 | `code` | 代码编写正确性 | 写 `is_prime(n)` | 关键字 `["def","%","return"]` |
| 通用问答 | `knowledge` | 事实知识 | 「日本首都？」 | 答案 `["东京","Tokyo"]` |
| 翻译 | `translation` | 中日/日中专业翻译 | Smartrans 题材翻译 | 关键译文词 `["見積","返信"]` |
| 指令遵循 | `instruction` | 格式/约束遵循 | JSON 输出、只答「是/否」 | 格式标记 `["{","}"]` |
| 长文本理解 | `longtext` | 长文档问答、摘要 | 长文关键信息提取 | 关键信息词 |
| 多轮对话 | `dialog` | 多轮一致性、指代消解 | 多轮问答 | 答案要点 |
| 信息抽取 | `extraction` | 实体/结构化提取 | 从文本抽实体 | 实体词 |

## 3. 题集设计规范

### 3.1 题目结构

```python
{
    "id": "reasoning-01",       # 唯一标识，维度-序号
    "dimension": "reasoning",   # 所属维度
    "prompt": "...",            # 提问内容
    "hints": ["8", "4"],        # 规则打分用的答案要点/关键词
}
```

### 3.2 编写原则

1. 题目需**单一明确**，避免多义。
2. `hints` 应选**客观可判定的要点**（数字、关键词、格式标记），避免主观表述。
3. 每题至少 1 个 hint；翻译题 hints 为关键译文词。
4. 按能力分层：本地小模型用**基础题**，云满血模型扩展**进阶题**（长文本、复杂推理、专业术语）。

## 4. 打分规则

### 4.1 规则分（客观，0~100）

**定义**：答案命中 `hints` 关键词的比例。

**公式**：

```
规则分 = 命中 hints 数 ÷ hints 总数 × 100
```

**匹配方式**：大小写不敏感的子串匹配（`hint.lower() in answer.lower()`）。

**示例**：`reasoning-01` 的 hints 为 `["8","4"]`，正确答案「苹果 8 个、橙子 4 个」命中 2 个 → 100 分；只答对苹果 → 50 分。

**局限**：子串匹配对数字存在误判（如 "8" 会命中 "18"），仅作初步客观基准，需与裁判分结合。

### 4.2 裁判分（主观，1~5）

**定义**：由裁判模型按统一模板对回答质量打分。

**评分标准**：

| 分 | 含义 |
|----|------|
| 5 | 完全正确且优质 |
| 4 | 基本正确 |
| 3 | 部分正确 |
| 2 | 大部分错误 |
| 1 | 完全错误 |

**裁判提示词模板**（`JUDGE_TEMPLATE`）：

```
你是一名严格的评测裁判。请根据题目要求和参考答案要点，评估下面模型回答的质量。
【题目】{prompt}
【参考答案要点】{hints}
【模型回答】{answer}
请给出 1 到 5 的整数评分（5=完全正确且优质，4=基本正确，3=部分正确，2=大部分错误，1=完全错误），并附一句简短理由。
请严格按以下格式输出：
分数：<1-5>
理由：<一句话>
```

**解析规则**：正则 `分数[:：]\s*([1-5])` 提取分数；解析失败回退为 3 分。

**裁判模型**：本地用 `qwen2.5:7b`；云满血阶段升级为更强的满血模型，减少自评偏差。

### 4.3 综合分（0~100）

**公式**：

```
综合分 = 0.5 × 规则分 + 0.5 × 裁判分 × 20
```

- 裁判分 × 20 将 1~5 映射到 0~100（`JUDGE_SCALE = 20`）。
- 无 hints 的题：综合分 = 裁判分 × 20。

**权重设计理由**：规则分客观、可解释，裁判分覆盖语义质量，各占 50% 平衡「可复现性」与「覆盖度」。

### 4.4 打分示例

| 题 | 规则分 | 裁判分 | 综合分 |
|----|--------|--------|--------|
| reasoning-01（hints 全命中，裁判 5 分） | 100 | 5 | 0.5×100 + 0.5×5×20 = 100 |
| translation-01（hints 全未命中，裁判 3 分） | 0 | 3 | 0.5×0 + 0.5×3×20 = 30 |

## 5. 判定基准

| 维度 | 通过阈值（建议） | 说明 |
|------|------------------|------|
| 脚本综合分 | ≥ 80 | 客观量化基准 |
| Agent 任务完成率 | ≥ 70% | 端到端任务 |
| 工具调用成功率 | ≥ 85% | Agent 可靠性 |
| 翻译人工评分 | ≥ 4/5 | 业务质量 |
| 成本 | ≤ 预算上限 | 超限告警 |

**冻结原则**：阈值在阶段一末评审冻结，后续阶段套用，保证横向可比，不得随意修改。

## 7. 评测流程

### 7.1 脚本评测流程

```
题集 ─▶ 生成回答(runner) ─▶ 规则打分 ─▶ 裁判打分 ─▶ 综合分 ─▶ 报告(report)
```

三步编排（`main.py`）：`run_all()` 生成 → `score_all()` 打分 → `generate()` 报告。

### 7.2 Agent 评测流程

```
任务调度 ─▶ LLM 决策(被测模型) ─▶ 工具/RAG ─▶ 结果采集 ─▶ 人工评审 ─▶ 评分
```

## 8. 质量控制

- **双盲评审**：Agent 关键输出由两位评审独立评分 + 交叉验证，取一致性结果。
- **自评偏差控制**：裁判模型与被测模型分离；云满血阶段用更强的独立裁判。
- **一致性校验**：规则分与裁判分差异过大（如规则 100 裁判 1）时人工复核。
- **版本冻结**：题集、基准、Agent 版本冻结后横向执行，保证可比。
- **护栏拦截处理**：被输入/输出护栏拦截的样本单独标记，不计入正常评分，单独统计拦截率与误拦率。

## 9. 指标定义与计算

| 指标 | 计算方式 |
|------|----------|
| 综合分 | 0.5×规则分 + 0.5×裁判分×20 |
| 分维度平均分 | 该维度所有题综合分均值 |
| 模型平均分 | 该模型所有题综合分均值 |
| 任务完成率 | 完成的任务数 ÷ 任务总数 |
| 工具调用成功率 | 成功调用数 ÷ 调用总数 |
| 响应延迟 | 请求发出到返回时间 |
| 吞吐 | token 数 ÷ 总耗时 |
| 每 token 成本 | 总费用 ÷ 总 token 数 |

## 10. 脚本评测技术实现

### 10.1 目录结构

```
scripts/eval/
├── main.py        # 入口，三步编排
├── config.py      # 全局配置
├── questions.py   # 题集
├── runner.py      # 生成回答
├── scorer.py      # 规则 + 裁判打分
├── report.py      # 报告聚合输出
└── results/       # 运行产物
```

### 10.2 模块与函数

| 模块 | 关键函数 | 说明 |
|------|----------|------|
| `config.py` | — | `OLLAMA_URL`、`AUTO_DISCOVER_MODELS`、`EXCLUDE_KEYWORDS`、`JUDGE_MODEL`、参数 |
| `questions.py` | — | `QUESTIONS`、`DIMENSIONS`、`DIMENSION_NAMES` |
| `runner.py` | `generate` / `discover_models` / `run_all` | 调用生成、自动发现模型、主流程 |
| `scorer.py` | `rule_score` / `judge_score` / `score_all` | 规则打分、裁判打分 |
| `report.py` | `total_score` / `build_report` / `generate` | 综合分、聚合、输出 |
| `main.py` | `main` | 编排 |

- `generate(model, prompt, params)`：POST `/api/generate`，对 r1 模型自动禁用思考并剥离 `<think>`。
- `discover_models()`：GET `/api/tags` 自动发现模型，按 `EXCLUDE_KEYWORDS` 排除 embedding 类。

### 10.3 数据流

```
main.py
  ├─ run_all()      ollama /api/generate ──> raw_results.json
  ├─ score_all()    读 raw ──> 规则+裁判 ──> scores.json
  └─ generate()     读 scores+raw ──> report.md + report.csv
```

### 10.4 断点续跑

- `raw_results.json` / `scores.json` 以 `(model, qid)` 为键去重。
- 跳过已存在且无 error 的条目，带 error 条目重跑；中断后重跑 `python main.py` 续跑。

### 10.5 扩展方式

| 需求 | 操作 |
|------|------|
| 新增题/维度 | `questions.py` 加题并在 `DIMENSIONS`、`DIMENSION_NAMES` 登记 |
| 新增模型 | `ollama pull` 后重跑（自动发现） |
| 排除模型 | `EXCLUDE_KEYWORDS` 加关键词 |
| 换裁判模型 | 改 `JUDGE_MODEL` |
| 调权重 | 改 `report.py` 的 `total_score()` 与 `JUDGE_SCALE` |

### 10.6 现成评测工具 promptfoo

除自研脚本外，还集成了开源评测框架 **promptfoo**（`npm install -g promptfoo`），与自研脚本互补：

| 维度 | 自研脚本（scripts/eval） | promptfoo |
|------|--------------------------|-----------|
| 打分方式 | 规则分 + 裁判分（1~5），综合分 | llm-rubric 断言（PASS/FAIL） |
| 输出 | report.md/csv（排名、分维度） | 通过率对比表 |
| 定位 | 细粒度量化打分 | 标准框架、快速横向对比 |

**配置**（`scripts/promptfoo/promptfooconfig.yaml`，由 `gen_config.py` 从 `questions.py` 自动生成）：

- `providers`：8 个模型经 **LiteLLM 网关** 对接（`openai:chat:<模型>`，`apiBaseUrl` 指向 `http://localhost:4000/v1`）
- `tests`：复用 24 题
- 断言：`llm-rubric`，judge 用 `qwen2.5:7b`（经 LiteLLM，输出 JSON 判定通过/失败）

> 所有评测工具（promptfoo、browser-use）统一经 LiteLLM 网关对接模型，不直接绑定 ollama，便于后续替换/扩展云满血模型。

**运行**：

```bash
cd scripts/promptfoo
python gen_config.py          # 从 questions.py 重新生成配置
promptfoo eval                # 完整评测 8 模型 × 24 题
promptfoo eval --filter-providers "qwen2.5:1.5b" --filter-range 0:10   # 部分评测
promptfoo view                # 查看结果
```

## 11. Agent 评测方法

### 11.1 通用 Agent

统一编排器，各模型仅替换「LLM 决策层」：

```
任务调度器 ─▶ LLM 决策层(被测模型) ─▶ 工具集(RAG/检索/计算)
                    ▲                      │
                    └──── 多轮记忆 ◀───────┘
```

- **任务集**：多步推理、检索问答、工具调用、长文档问答。
- **指标**：任务完成率、工具调用成功率、检索命中率、多轮一致性、耗时。

**实现框架**：采用开源 **browser-use**（`pip install browser-use`），让模型操控浏览器完成真实任务：

- 模型接入：经 **LiteLLM 网关** 对接（`ChatOpenAI(base_url="http://localhost:4000/v1")`），示例见 `scripts/agent/run_agent.py`。
- 任务类型：网页检索、表单填写、多步操作、信息抓取。
- 指标：任务完成率、步骤成功率、耗时。

### 11.2 业务场景 Agent（Smartrans）

选定 Smartrans 作为业务场景评测对象，以实际业务题材进行转换精度评测，人工双盲评分 + 自动指标。

### 11.3 人工评审

- 对 Agent 关键输出进行**人工双盲评分**（两位评审独立评分 + 交叉验证）。
- 评分维度：正确性、完整性、可用性、效率（1~5 分）。

## 12. 安全护栏评测（延后处理）

> 护栏的实现与评测延后至阶段三及以后处理，本节仅作设计预留。

### 12.1 评测目标

量化护栏的**召回率**（拦截有害内容的能力）与**误拦率**（不误伤正常内容），作为护栏质量判定基准。

### 12.2 数据集设计

| 数据集 | 样本数 | 应判 | 用途 |
|--------|--------|------|------|
| 攻击输入集 | 50+ | 拦截 | 测输入护栏召回（Prompt 注入、越权、敏感词） |
| 有害输出集 | 50+ | 拦截 | 测输出护栏召回（有害内容、PII 泄露） |
| 正常样本集 | 100+ | 放行 | 测误拦率（正常业务请求/输出） |

### 12.3 评测指标

| 指标 | 公式 | 说明 |
|------|------|------|
| 拦截率（召回率） | TP ÷ (TP + FN) | 有害样本被正确拦截的比例 |
| 误拦率（假阳性率） | FP ÷ (FP + TN) | 正常样本被误拦的比例 |
| 精确率 | TP ÷ (TP + FP) | 拦截中真正有害的比例 |
| F1 | 2×P×R ÷ (P+R) | 精确率与召回率的调和均值 |

其中 TP=正确拦截、FN=漏拦、FP=误拦、TN=正确放行。

### 12.4 评测流程

```
构造样本集 ─▶ 过护栏 ─▶ 统计 TP/FP/FN/TN ─▶ 计算指标 ─▶ 护栏评测报告
```

- 判定标准：护栏**拦截率 ≥ 95%**、**误拦率 ≤ 5%** 为通过。
- 未达标时扩充敏感词库 / 收紧 PII 规则，回归复测。
